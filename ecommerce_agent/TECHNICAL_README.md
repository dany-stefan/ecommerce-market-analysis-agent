### Step 2: Configuration

Edit the `.env` file to customize the agent behavior:

```bash
# Language Model Configuration
OPENAI_API_KEY=your_openai_api_key_here
LLM_MODEL=gpt-4                    # or gpt-3.5-turbo for faster/cheaper
LLM_TEMPERATURE=0.7                # Creativity level (0.0-1.0)
MAX_TOKENS=2000                    # Response length limit

# Agent Behavior
MAX_ITERATIONS=5                   # Maximum tool orchestration cycles
VERBOSE_LOGGING=true               # Detailed execution logs
```

**Configuration Options Explained:**

- `LLM_MODEL`: Choose between GPT-4 (higher quality) or GPT-3.5-turbo (faster, cheaper)
- `LLM_TEMPERATURE`: Controls randomness (0.0 = deterministic, 1.0 = creative)
- `MAX_ITERATIONS`: Prevents infinite loops in agent reasoning
- `VERBOSE_LOGGING`: Shows detailed tool execution steps

## Design Decisions Log

### 1. Modular Architecture
**Decision**: Separate agent logic, tools, and utilities into distinct modules.

**Justification**: This separation allows:
- Easy testing of individual components
- Reusability of tools in other projects
- Clear separation of concerns
- Simplified debugging and maintenance

### 2. Tool-First Approach
**Decision**: Design individual tools as independent, composable units.

**Justification**: Following the assignment's emphasis on orchestration:
- Each tool does one thing well
- Tools can be combined in different ways
- Easy to add new capabilities without modifying existing code
- Facilitates future integration scenarios

### 3. Four-Tool Architecture
**Decision**: Create four specialized tools aligned with the market analysis workflow:
1. **Product Data Collector**: Gathers product information, pricing, specifications (mock data + API-ready)
2. **Sentiment Analyzer**: Processes customer reviews using LLM-based analysis
3. **Competition Analyzer**: Compares similar products, market positioning
4. **Report Generator**: Synthesizes insights using LLM for structured recommendations

**Justification**: This architecture:
- Maps directly to the business requirements
- Creates a clear analysis pipeline
- Each tool has a distinct, measurable output
- Allows for parallel execution where appropriate
- Simple enough to explain in a presentation
- **LLM Integration**: Tools 2 & 4 use LLMs with task-specific prompts

### 4. Error Handling Strategy
**Decision**: Multi-layer error handling approach:
- Tool level: Try-catch with graceful degradation
- Agent level: Continue with partial results if one tool fails
- User level: Clear error messages with actionable feedback

**Justification**: Production-ready systems must handle failures gracefully without crashing the entire pipeline.

### 5. Extensibility Patterns
**Decision**: Plugin-style tool registration with clear interfaces.

**Justification**:
- New tools can be added without modifying agent code
- Tools can be developed and tested independently
- Easy to swap implementations (mock → real APIs)
- Supports future features like tool versioning, A/B testing
